# Автоматизация обработки тикетов поддержки

## Проблема

Крупный онлайн-сервис получает около 200 тысяч тикетов поддержки в день через чат, email, веб-форму и мобильное приложение. Часть обращений типовая и может быть обработана быстрее, но рискованные, неоднозначные или содержащие персональные данные нельзя безопасно закрывать автоматически. Система должна одновременно ускорять классификацию и маршрутизацию, контролировать стоимость генерации ответов и сохранять аудит автоматических решений.

## Что делает предлагаемая система

Система принимает тикет, нормализует его и присваивает идентификатор запроса, выполняет проверки PII и жёстких рисков, а затем на горячем пути определяет тему, маршрут и уровень риска лёгкими детерминированными правилами и моделью классификации. Безопасные и достаточно уверенные случаи передаются в асинхронный контур: поиск по базе знаний или похожим решённым тикетам, подготовка черновика ответа и проверка его безопасности и обоснованности. Низкая уверенность, рискованная категория, отсутствие достаточных доказательств или отказ внешней зависимости переводят тикет оператору; каждое решение записывается в аудит.

## PoC и целевая архитектура

PoC подтвердит вертикальный сценарий на локальных и детерминированных компонентах: mock-ticket, простая классификация и правила риска, небольшой локальный поиск по базе знаний, черновик или маршрут, аудит, happy path и эскалация рискованного либо low-confidence тикета.

Целевая архитектура дополнительно предусматривает масштабируемое stateless-обслуживание горячего пути, durable-хранилище событий и тикетов, очередь для медленного контура, production-модели, PII-контроль, мониторинг и операторский интерфейс. Эти production-компоненты в рамках 4-часового задания не реализуются.

## Скоуп на 4 часа

В PoC входят mock-ticket, request identity, детерминированные risk rules, topic/routing PoC-классификация, локальная lexical retrieval-база, детерминированный evidence-grounded draft generator, audit log, happy path и risky/HITL эскалация.

Только проектируются внешняя асинхронная LLM-интеграция, реальная реализация LLM outage/retry/backpressure, production broker и durable storage, production model serving, отдельный PII-сервис, полноценный monitoring stack, обучение моделей, операторский UI и MLOps-пайплайн. Поведение при LLM outage демонстрируется на уровне архитектуры и дизайна, поскольку локальный PoC намеренно не имеет внешних зависимостей.

`LOCAL_DECISION_BOUNDARY=0.60` и `MIN_RETRIEVAL_SCORE=0.20` — demo-only fixture boundaries; они не являются калиброванными production thresholds.

## Бизнес-ценность

Система снижает нагрузку на операторов за счёт ускорения типовых обращений и подготовки проверяемых черновиков. Быстрая маршрутизация помогает соблюдать SLA первого ответа даже при всплесках нагрузки. Ограничение автоматизации рискованными категориями и обязательный аудит защищают CSAT, SLA и безопасность пользователей. Асинхронный вызов LLM только там, где он действительно добавляет ценность, ограничивает стоимость и позволяет корректно переживать отказ внешнего сервиса.

Подробности целевой архитектуры и выбора ML/LLM-подходов находятся в [docs/architecture.md](docs/architecture.md) и [docs/ml.md](docs/ml.md).

## Запуск PoC

Требуется Python 3.9+; проверено на Python 3.9.6 и Python 3.12; внешние зависимости не нужны.

```bash
python3 --version
python3 demo.py
```

Команда последовательно показывает безопасный FAQ happy path с локальным evidence и детерминированным черновиком, а также risky path с `needs_review` и маршрутом оператору. В PoC classifier — детерминированная keyword-логика, retrieval — маленький локальный lexical token-overlap поиск, generator — локальный deterministic mock/template; production counterparts описаны в документации.
