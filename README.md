# Автоматизация обработки тикетов поддержки

## Проблема

Крупный онлайн-сервис получает около 200 тысяч тикетов поддержки в день через чат, email, веб-форму и мобильное приложение. Часть обращений типовая и может быть обработана быстрее, но рискованные, неоднозначные или содержащие PII, которую нельзя безопасно минимизировать, нельзя закрывать автоматически. Система должна ускорять классификацию и маршрутизацию, контролировать стоимость генерации ответов и сохранять аудит автоматических решений.

## Что делает предлагаемая система

Система принимает тикет, нормализует его и присваивает идентификатор запроса, выполняет проверки PII и жёстких рисков, а затем на горячем пути определяет тему, маршрут и уровень риска лёгкими детерминированными правилами и моделью классификации. Безопасные и достаточно уверенные случаи передаются в асинхронный контур: поиск по базе знаний или похожим решённым тикетам, подготовка черновика ответа и проверка его безопасности и обоснованности. Низкая уверенность, рискованная категория, отсутствие достаточных доказательств или отказ внешней зависимости переводят тикет оператору; каждое решение записывается в аудит.

## PoC и целевая архитектура

PoC подтверждает вертикальный сценарий на локальных и детерминированных компонентах: тестовое обращение, классификация и правила риска, небольшой локальный поиск по базе знаний, черновик или маршрут, аудит, happy path и эскалация рискованного либо low-confidence тикета.

Целевая архитектура дополнительно предусматривает масштабируемый горячий путь без состояния на экземпляре сервиса, надёжное хранилище событий и тикетов, очередь для медленного контура, боевые модели, контроль PII, мониторинг и операторский интерфейс. Эти компоненты в рамках 4-часового задания не реализуются.

## Скоуп на 4 часа

В PoC входят тестовое обращение, идентификатор запроса, детерминированные правила риска, классификация темы и маршрута, локальный лексический поиск, детерминированный черновик на основе найденной статьи, журнал аудита, обычный сценарий и эскалация рискованных случаев оператору.

Только проектируются внешняя асинхронная LLM-интеграция, реальная реализация LLM outage/retry/backpressure, production broker и durable storage, production model serving, отдельный PII-сервис, полноценный monitoring stack, обучение моделей, операторский UI и MLOps-пайплайн. В PoC отказ локального генератора воспроизводится детерминированно; реальные outage/retry/backpressure остаются частью архитектурного дизайна.

`LOCAL_DECISION_BOUNDARY=0.60` и `MIN_RETRIEVAL_SCORE=0.20` — demo-only fixture boundaries; они не являются калиброванными production thresholds.

## Бизнес-ценность

Система снижает нагрузку на операторов за счёт ускорения типовых обращений и подготовки проверяемых черновиков. Быстрая маршрутизация помогает соблюдать SLA первого ответа даже при всплесках нагрузки. Ограничение автоматизации рискованными категориями и обязательный аудит защищают CSAT, SLA и безопасность пользователей. Асинхронный вызов LLM только там, где он действительно добавляет ценность, ограничивает стоимость и позволяет корректно переживать отказ внешнего сервиса.

Подробности целевой архитектуры и выбора ML/LLM-подходов находятся в [docs/architecture.md](docs/architecture.md) и [docs/ml.md](docs/ml.md).

## Запуск PoC

Требуется Python 3.9+; проверено на Python 3.9.6 и Python 3.12; внешние зависимости не нужны.

```bash
python3 --version
python3 demo.py
```

Команда последовательно показывает безопасный FAQ-сценарий с локальным evidence и детерминированным черновиком, рискованный сценарий с `needs_review` и маршрутом оператору, а также отказ генератора с безопасной эскалацией. В PoC классификатор использует ключевые слова, поиск — пересечение токенов в четырёх локальных статьях KB, а генератор — локальный шаблон; боевые варианты описаны в документации.

## Быстрая проверка

```bash
python3 demo.py
python3 evaluate.py
python3 -m unittest discover -s tests -v
```

`demo.py` показывает happy, risky/HITL и отказ генератора; `evaluate.py` запускает синтетическую демонстрационную проверку; `unittest` проверяет ключевые инварианты PoC.

### Что доказывает PoC

- детерминированную маршрутизацию и проверку риска на fast path;
- черновик на основе найденной статьи;
- HITL для hard-risk;
- безопасную деградацию при недоступности генератора;
- audit trail;
- синтетическую демонстрационную проверку.

## Ограничения PoC

- Риск определяется поиском подстрок и правилами.
- Санитизация PII показывает только email и телефон.
- Confidence — иллюстративный score, а не calibrated probability.
- Retrieval — пересечение токенов по четырём локальным статьям KB.
- Grounding gate проверяет, что детерминированный черновик содержит найденное evidence; это не семантическая оценка LLM.
- Отказ генератора — детерминированная локальная симуляция.
- Очередь, retries и идемпотентные внешние side effects относятся только к target design.
- Evaluation синтетический и малый; он не оценивает production quality.
